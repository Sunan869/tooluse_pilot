W8 v1 frozen design before API calls
Same 8 students / 18 grade records / 8 advisory cache rows; static vs one deterministic revision publication. No pagination or uncertain transactions added.
Task: rank active B2 latest published valid grades, score descending / student_id ascending. Static remains R1. Dynamic publishes R2 once immediately after the first grades read (or before first write if no grades read). R2 replaces s05 B2 score 90 with 96, revision 2. This is a deterministic environment change, not a hidden score change.
Every read includes read_revision and current_revision. The triggering read explicitly says stale=true and gives status recovery guidance. get_status returns current revision, changed record IDs and one-time update status, never oracle answers. Re-read current authoritative data after change. The data is thereafter stable. Cache remains advisory and may lag. Complete authoritative rows and point lookup are always reachable.
write_submission requires expected_revision; stale revision returns a recoverable response with current revision and no file modification. It checks version, not answer. Wrong answers with current revision can be overwritten before finish. finish is explicitly irreversible terminal commit, requires a saved submission at current revision, never checks oracle, and runner stops immediately with no further API call or queued tool execution. A rejected stale finish is nonterminal. Report answer_correct, task_completed, stop_reason and budget_exhaustion separately. Do not relabel historical W7 runs.
Same prompt/schema/budget across conditions: 25 actual API attempts / 80 tools, specified Flash only thinking=false. Static baseline before dynamic, independent repeat for a final failure. Small row-order seed robustness check if warranted. No GPT until valid paired and reproduced failure admission.
